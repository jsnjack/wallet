Wallet: design

A local-first Android app for loyalty cards, vouchers, tickets and boarding passes, built for One UI 9 (Android 17) on Galaxy phones, with sync through your Google Drive. The goal is that a code is on screen within a second of reaching for the phone.

The grid makes every card one tap from its code and shows about eight cards without scrolling, sorted by how often you use them. The “Up next” row appears only when one of the rules below fires; otherwise it is hidden, so a wrong guess never pushes your cards down. Search sits in the thumb zone at the bottom: tap it, or just start typing, and the grid filters as you type.

The page background follows the phone’s light or dark mode, while cards keep their brand colours in both. In dark mode the tiles lose their shadow and the “Up next” row turns dark grey, so the brand colours carry the screen.

When “Up next” appears

Only one row shows. If several rules fire, the row shows the highest one and a “+1” badge; swiping the row moves to the next.

PriorityRuleShowsWindow

2Event ticketThe ticketThe day of the event

Rule 3 needs the location permission, is off until you turn it on, and reads the location only when the app opens (no background tracking). The places it learns stay on the phone and are not synced.

Design principles

  1. Code in one tap or less. No network, no account check and no animation longer than 150 ms on the path from icon to code. Sync runs after the screen is drawn and never blocks it.
  2. One layout for every card. Name, code and number always sit in the same place. Type-specific details (expiry, PIN, balance, seat, gate) go next to or below the code, never in front of it.
  3. Works offline. Everything lives on the phone; Drive holds a synced copy.
  4. Thumb zone. Search, scan and actions at the bottom, as in One UI; the top holds only titles.
  5. Scanner-friendly. White quiet zone around the code, brightness to maximum, screen kept awake while the code is shown.

The code screen

Every path ends on this screen. The brand colour fills the top for recognition; the code sits on white below it. Swipe left or right to move to the next card without going back.

Loyalty card (EAN-13)
One-time voucher (QR): expiry, PIN, “Mark as used”
Boarding pass (Aztec): route, gate, seat, trip legs
Gift card (Code 128): balance shown, code hidden until fingerprint
Event ticket (QR): date, entrance, seat
  • Brightness: the screen goes to full brightness while the code is shown and returns to normal when you leave.
  • Vouchers: a reminder the day before expiry; “Mark as used” moves the voucher to an archive.
  • Locked cards: any card can require a fingerprint. Gift cards default to locked because the number and PIN are spendable money. The balance stays visible; you update it by hand after shopping.
  • Tickets and passes move to the archive the day after their date.

Boarding passes

Airlines encode boarding passes in a standard text format called IATA BCBP (Bar Coded Boarding Pass), printed as a PDF417, Aztec or QR code. When the app scans one, it reads the passenger name, booking reference (PNR), departure and arrival airports, airline, flight number, date, cabin and seat, and builds the flight card automatically. A bundled airport table turns “AMS” into “Amsterdam”.

What the barcode does not contain

The BCBP code holds the date but not departure time, boarding time or gate. A .pkpass file from the airline usually has them; otherwise you type them in. Live gate changes would need a flight-status API later.

  • Travel day: from 24 hours before the flight date the pass takes the “Up next” row and gets a live notification.
  • Trips: several legs or passengers on one booking group into one trip; swipe between them.
  • Afterwards: the pass moves to the archive the day after the flight.

Google Drive sync

The phone’s own database stays the main copy, so the app works offline and opens without waiting for the network. Google Drive holds a synced copy in its app data folder: a hidden folder that only this app can see, which does not appear in your Drive file list and uses a few hundred kilobytes of your Drive storage.

How a sync works

  1. When: after the app has drawn its first screen, a few seconds after you change a card, and every few hours in the background when the phone has network.
  2. What moves: each card is one small file, and each logo or photo is one file named by its content hash. Drive’s change list tells the app which files changed since the last sync, so it never downloads everything again.
  3. Conflicts: every card carries a “last changed” time. If the same card changed on two devices, the newer change wins for that card. For one person with two devices this is enough; a merge screen would be overkill.
  4. Deletes: a deleted card becomes a small “deleted” marker instead of disappearing, so the other device learns about the delete instead of uploading the card again.
  5. Not synced: how often you use each card and the places learned for “Up next”. They change every time you open a card, and location history is better kept on the phone.

Encryption

Decision: no passphrase. Sync files are stored as they are, protected by your Google account and Google’s storage encryption. Setup on a new device is just “sign in, allow access”, and there is no passphrase to lose.

The trade-off: Google, or anyone who gets into your Google account, can read the cards, including booking references and gift card PINs. A strong Google password with 2-step verification is the protection that matters here. The cards are stored as one small file each, so client-side encryption can be added later without changing the sync design.

The export file is still encrypted with a password you choose when exporting, because that file can end up anywhere.

Sync is set up on first run or later from Settings: pick your Google account and allow access to the app folder. The same two steps on a second device download your cards.

The status card turns amber when the last sync is older than a day, and red when sync fails (for example, if access was removed in your Google account settings), with a button to fix it. Sync problems never block opening a card.

The encrypted export file stays as a backup that does not depend on Google.

One-off Google Cloud setup

Drive access needs a Google Cloud project that identifies the app. This is free and takes about 15 minutes:

  1. Create a project in the Google Cloud console and enable the Google Drive API.
  2. Configure the OAuth consent screen (the “allow this app to…” page) as External, with only the drive.appdata scope.
  3. Create an Android OAuth client with the package name io.github.jsnjack.wallet and the SHA-1 fingerprint of each signing key (debug and release).
  4. Set the consent screen’s publishing status to In production. In “Testing” status, Google drops the app’s access 7 days after you approve it, and sync would stop every week.

drive.appdata is a non-sensitive scope (Google’s scope list), so publishing should not need Google’s app review. The 7-day limit is described in Google Cloud help.
